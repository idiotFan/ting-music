## 可复现的问题

### R1 · P2 · 移除的歌曲会被播放历史重新加入队列

位置：`src/main.ts:601–606`、`src/main.ts:719–724`，以及 `play()` 中自动入队逻辑。

复现：依次播放 1、2、3，在队列中移除 2，再按上一首。实际播放 2，并被 `play()` 重新插入队列。移除只修改 `queue`，没有清理 `playbackHistory`；`skip()` 又优先使用历史且不检查成员资格。

建议：定义队列编辑与历史导航的一致规则，移除歌曲时清理有效导航项，或在历史导航时跳过已移除歌曲；避免历史导航静默改变用户刚编辑的队列。额外浏览器探针已复现。

### R2 · P2 · 移除当前歌曲后，顺序播放在曲末停止

位置：`src/main.ts:870–873`。

复现：队列 1、2、3，播放 1 时将其移出队列，但让它继续播放。到曲末时当前歌曲在队列中的索引为 -1，`ended` 分支不会进入下一首；2、3 仍在队列但播放停止。

建议：保留当前播放游标或明确记录移除后的后继歌曲，不依赖当前歌曲一定在队列中。额外探针使用 20 秒静音音频并跳到曲末，确认仍停留在歌曲 1。

### R3 · P2 · 登录弹窗会丢弃尚未完成的账号恢复

位置：`src/main.ts:910–915`、`src/main.ts:995–996`。

复现：将启动时 `account_status` 延迟 1.8 秒，立即打开再关闭登录框。`startLogin()` 增加 `authVersions`，有效的恢复结果随后被 `initialize()` 丢弃；取消扫码没有重查账号。界面持续显示“登录”，已有钥匙串会话并未失效。

建议：显式区分恢复中、未登录、扫码中、已登录；恢复尚未结束时不直接开启新登录，或取消扫码后重新验证当前会话。额外浏览器探针已复现。

### R4 · P2 · 下载账号来源与界面登录状态不一致

位置：`resources/downloader/download_one.py:34–38`、`112–119`，`src-tauri/src/download.rs:60–72`。

直接 QQ 下载使用 Ting 当前 QQ 会话；网易云下载无当前 MUSIC_U 时会回退到旧 musicfox 网易云 cookie，网易云的 QQ 补源则读取旧 `qq_cookie.txt`，没有使用 Ting 的 QQ 会话。因此可能出现“当前双账号均可播放但补源失败”，以及“应用已退出网易云，下载却仍使用另一个旧账号”的表现。

这来自早期复用音乐库流程的兼容实现，现在需要和双账号模型统一。离线探针已确认：无当前 MUSIC_U、旧文件存在时，会调用旧账号构造器；未读取或输出真实凭据。建议默认使用当前会话，旧凭据兼容改为明确可选的来源并展示状态。

### R5 · P2 · 大列表选中操作包含二次复杂度的全量扫描

位置：`src/main.ts:274–294`。

`syncRows()` 遍历所有 DOM 行，每一行再执行 `favorites.some()` 与 `list().find()`。单击选择、切歌、收藏等高频操作都会运行它；列表也未虚拟化。

本机 Chromium、模拟数据、收藏数等于歌曲数，直接测量点击事件同步处理时间：

| 歌曲数 | 5 次点击耗时范围 |
| --- | --- |
| 1,500 | 33.0–35.8 ms |
| 5,000 | 361.6–375.8 ms |

这些是本机浏览器测量值，不是 macOS WebView 基准，未据此推断具体内存占用。建议用 Set / Map 建立索引，选中变化仅更新前后两行；随后评估分页渲染或列表虚拟化。

### R6 · P3 · QQ FLAC 的内嵌来源注释错误

位置：`resources/downloader/library_tools.py:292`。

标签函数无条件写入 `netease:{id}`。已检查 QQ 直接下载的《红尘客栈》，实际 COMMENT 为 `netease:5177680 source:qq level:master`，把 QQ ID 标记成网易云 ID。文件名和来源 JSON 的平台信息正确，但下游读取音频注释会得到错误标识。

建议：将请求平台、原始 ID、实际音源平台、匹配后的平台 ID 分字段传递，按正确命名空间写标签。

## 工程质量与发布缺口

- `main.ts` 同时管理视图、播放器、历史、队列、账号、分页和下载状态；大量散落的可变变量使上述竞态难以推理。优先抽取播放器状态机、账号控制器和库数据存储，无需更换 UI 框架。
- 歌单、歌词、主题模块的许多函数挤在单行，增加审阅和修改成本。应统一格式化并给平台响应建立明确类型；当前很多 Python / TypeScript 边界仍依赖动态对象。
- 应用打包了 Python 依赖，未打包解释器；QQ 只寻找两个 macOS Python 3.12 绝对路径。Linux / Windows 还需改资源构建、解释器查找、打包目标与凭据存储。非 macOS `persist(None)` 返回错误，会使 QQ 退出在清理内存前返回；属于移植前必须修正的分支。
- 当前没有 CI 工作流、稳定版发布流水线或自动更新。构建前未强制运行 Python 资源完整性检查；准备资源仍是文档规定的独立步骤。
- 当前 `/Applications` 与项目根目录 `.app` 均为 0.6.0，源码清单为 0.7.0，运行中的预览又是另一份构建。新歌词等源码功能不能以旧应用进程的表现代替验证；需要统一版本和交付路径。
- 本机存储没有版本化迁移、导出备份或跨设备同步。当前范围内不是新增缺陷，但应作为数据可靠性工作明确记录。
